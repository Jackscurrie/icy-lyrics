# Android font scaling on iOS

The frozen Android app resolves Compose UI **1.11.0**; Material 3 has its own version. Its `AndroidDensity` uses the AndroidX `FontScaleConverterFactory` and `FontScaleConverterTable` implementation shipped in `ui-unit-android`, including on the API 36 reference emulator. This is not an inference from an Android version alone.

Primary source: [Google Maven ui-unit-android 1.11.0 sources](https://dl.google.com/dl/android/maven2/androidx/compose/ui/ui-unit-android/1.11.0/ui-unit-android-1.11.0-sources.jar). Exact archive SHA-256: `c6e2ea6314bfc45e27c5f28fda333afe2ed76748a004eec95f86cbdab099a6ff`. The retained source-file hashes and actual capture values are in [the evidence fixture](../tests/fixtures/android36-large-text-font-conversions.json). The adapter is derived from the Apache-2.0 Android Open Source Project implementation, with its copyright/license notice retained in the source.

The original curves map nine SP anchors (8, 10, 12, 14, 18, 20, 24, 30, 100) to DP at font scales 1.15, 1.3, 1.5, 1.8 and 2.0. Android enables nonlinear conversion at 1.03. Values between anchors use piecewise linear interpolation in Float arithmetic; lower values interpolate from zero, upper values use the last anchor's ratio, and negative values retain their sign. DP→SP uses the same table with the axes exchanged. Intermediate scales interpolate curves, including from the identity curve below 1.15. Lookup keys truncate `fontScale*100`, matching the original. Above the last key, conversion becomes linear.

The port keeps immutable per-scale curves instead of the upstream process-wide cache. It interpolates between the original reviewed anchor tables. This matches a fresh upstream converter at every tested scale and avoids tiny floating-point differences caused by the history of previously cached intermediate scales. The captured scale 1.8 directly uses a fixed original table, so cache history does not affect it.

`androidFontScalingDensity` changes only `TextUnit.toDp` and `Dp.toSp`, preserving physical density and the reported native Dynamic Type font scale. Below the nonlinear threshold it returns the original Density object. Android production code never invokes the adapter. iOS production and UIKit fixture entry points use the same `ProvideAndroidFontScaling` composition provider; the isolated native raster test host uses the same density adapter. Font assets, font weights, tracking, baseline positioning and style size constants are untouched.

This insertion covers text rendering and measurement: pinned [CMP 1.11.1 ParagraphBuilder](https://github.com/JetBrains/compose-multiplatform-core/blob/v1.11.1/compose/ui/ui-text/src/skikoMain/kotlin/androidx/compose/ui/text/platform/ParagraphBuilder.skiko.kt) converts font size, explicit SP line height, SP letter spacing and placeholders through its supplied Density. It does not reconstruct a linear Density internally. This also preserves relative EM behavior.

The custom lyric canvas has two SP-based animation offsets. CMP `CanvasDrawScope` forwards only numeric density and font scale, so invoking `TextUnit.toPx` directly on that scope would lose the custom converter. Both offsets use the line's `TextLayoutInput.density`, matching the density that measured the glyphs. The lyric layout cache is keyed by its text measurer so live Dynamic Type changes cannot reuse measurements from the previous scale. Presentation zoom ratios still multiply SP before conversion. Portrait/mixed layout reservation and scrub-popup sizing intentionally retain the original Android DP-based font-scale heuristics. Font resolver setup does not replace Density or multiply font sizes.

At measured density 3 and font scale 1.8, the original Android fixture reports 16sp→78px, 28sp→102.399994px and 64sp→199.4057px. The eleven actual sample values are retained in the evidence fixture and asserted as exact Float bits. At scale 1.0 all eleven original measurements already agreed; returning the original Density preserves that behavior.

Common tests cover actual captured conversions, normal-size identity, intermediate scales/sizes, boundaries, negative values and forward/inverse round trips. A separate JVM test executes the actual pinned AndroidX converter and compares both directions across 17 scales and 24 sizes. Native source compilation and macOS runtime results must be reported separately: these arithmetic tests do not establish screenshot parity, glyph shaping parity, or physical iPhone validation.
